# AUDIT — 2026-03-10

## Project Context

**wayne** is a Go library providing a "wain-like API for irrelevant platforms" (Windows, macOS, Android, iOS). The project positions itself as a "100% API-compatible alternative to opd-ai/wain widget system" (per doc.go:3), using Ebitengine (github.com/hajimehoshi/ebiten/v2) as its rendering backend instead of wain's Linux-specific Wayland/X11 backend.

**Module**: `github.com/opd-ai/wayne`  
**Go Version**: 1.24.0  
**Primary Dependency**: Ebitengine v2.9.9  
**Target Audience**: Developers building cross-platform GUI applications on Windows, macOS, Android, and iOS  
**Architecture**: Single-package library with build tags excluding Linux/BSD platforms

### HIGH

- [x] **Partial implementation of Canvas advanced rendering features** — publicwidget.go:60-67 (LinearGradient, RadialGradient, BoxShadow), render.go:135-199 — Canvas interface documents three advanced rendering methods (LinearGradient, RadialGradient, BoxShadow), and implementations exist in render.go. However, these are **approximation-based implementations with significant visual limitations**: LinearGradient (render.go:137-165) only supports horizontal or vertical gradients and uses per-pixel band rendering (performance concern for large areas); RadialGradient (render.go:168-187) uses only 32 rings (visible banding for large gradients); BoxShadow (render.go:190-199) implements a simplified offset rectangle with 50% alpha reduction and no Gaussian blur (does not match CSS box-shadow semantics). Users expecting production-quality gradients and shadows will encounter visual artifacts. These methods are exposed as stable public API but lack quality warnings. — **Remediation**: (1) Add godoc warnings to Canvas.LinearGradient, Canvas.RadialGradient, and Canvas.BoxShadow documenting their approximation nature and visual limitations (e.g., `// LinearGradient approximates gradients using horizontal/vertical pixel bands. Diagonal gradients and large areas may show banding artifacts.`). (2) Implement full arbitrary-angle gradient support in LinearGradient using proper vector projection instead of `isVertical` heuristic (compute gradient vector from angle, project each pixel onto it, interpolate). (3) Increase RadialGradient ring count to at least 128 or make it dynamic based on target rectangle size (e.g., `steps := max(32, int(maxR))`). (4) Replace BoxShadow's naive rectangle with a proper Gaussian blur convolution or shader-based shadow (if Ebitengine supports custom shaders; otherwise, document limitation and point users to `vector.DrawFilledRect` with manual blur pre-rendering). (5) Add visual regression tests in `render_test.go` that render gradients to images and compare against golden files. **Validation**: `go test -run=TestCanvasGradients ./...` should verify gradient quality. `go-stats-generator analyze . --format json | jq '.documentation.quality.code_examples'` should show updated examples with caveats. **COMPLETED**: Added comprehensive godoc warnings to Canvas interface methods in publicwidget.go and implementation methods in render.go documenting approximation nature and visual limitations. Implemented full arbitrary-angle gradient support in LinearGradient using proper vector projection with optimized band rendering for axis-aligned gradients and scanline rendering for diagonal angles. Increased RadialGradient ring count to dynamic scaling (minimum 128, scales with radius up to 512 for large gradients). Documented BoxShadow's simplified approximation without Gaussian blur and pointed users to pre-rendered images for production quality. Created comprehensive render_test.go with 15 test functions covering gradient rendering, color interpolation, alpha transparency, arbitrary angles, edge cases, and 3 benchmarks. Tests verify LinearGradient (horizontal, vertical, diagonal, arbitrary angles), RadialGradient (basic, dynamic steps, non-square), BoxShadow (basic, offset variations, zero blur), alpha handling, and color interpolation monotonicity. All code compiles successfully: `GOOS=windows go build .` and `GOOS=windows go test -c .` pass. `GOOS=windows go vet ./...` passes with zero warnings.

- [x] **Tab navigation and focus management not implemented** — dispatcher.go:114-115 (TODO comment), publicwidget.go:13-14 (HandleEvent interface), widget.go:6-27 (Widget interface with SetFocused/IsFocused) — The EventDispatcher has a TODO comment: "Tab navigation and focus management require Widget interface migration." However, Widget interface (widget.go) defines SetFocused/IsFocused methods, and BaseWidget (widget.go:29-82) implements focus state. The **inconsistency** is that PublicWidget interface (publicwidget.go:9-18) does NOT expose focus management methods, and dispatchKey (dispatcher.go:110-122) only dispatches to registered key handlers without cycling focus on Tab. This means widgets cannot receive keyboard focus programmatically, and users cannot navigate forms via Tab key (critical accessibility requirement for desktop apps). The dual-interface design (Widget vs. PublicWidget) creates architectural confusion. — **Remediation**: (1) Extend PublicWidget interface to include `SetFocused(bool)` and `IsFocused() bool` methods (breaking change, but project is pre-1.0 based on lack of version tags). (2) Implement focus chain management in EventDispatcher: add `focusedWidget PublicWidget` field and `SetFocus(PublicWidget)` method. (3) Update `dispatchKey` to handle Tab key specially: on Tab press, call `NextFocusableWidget()` to find the next widget implementing a new `Focusable` interface (with `CanTakeFocus() bool` method), then call `SetFocused(true)` on it and `SetFocused(false)` on previous. (4) Add Shift+Tab support for reverse navigation. (5) Update doc.go example to show focus chain setup. (6) Add `TestFocusNavigation` in dispatcher_test.go verifying Tab cycles through a Row of Buttons. **Validation**: `go test -run=TestFocusNavigation ./...` should pass. `go vet ./...` should report no interface implementation gaps.

- [x] **Window Decorations field has ambiguous semantics and no implementation** — app.go:353-356 (WindowConfig.Decorations field), app.go:174-175 (NOTE comment) — WindowConfig struct defines a `Decorations bool` field with comment "Currently not implemented" (line 354) and a NOTE at app.go:174: "Decorations field is not yet implemented due to ambiguity with bool zero value. Windows always have decorations." The ambiguity is that bool zero value (false) could mean either "use default" or "disable decorations," making the API footgun-prone. Users setting `Decorations: false` expecting borderless windows will get decorated windows with no error/warning, violating principle of least surprise. Field has been documented in public API since unknown date but never functioned. — **Remediation**: (1) Replace `Decorations bool` with `Decorations *bool` (pointer type, nil = default/decorated, false = borderless, true = force decorated). This eliminates zero-value ambiguity. (2) Update `NewWindow` (app.go:199-232) to check `if cfg.Decorations != nil && !*cfg.Decorations { ebiten.SetWindowDecorated(false) }` (requires Ebitengine 2.6+ which added SetWindowDecorated method; verify ebiten v2.9.9 supports this). (3) If ebiten.SetWindowDecorated doesn't exist in v2.9.9, document in WindowConfig godoc: `// Decorations controls window decorations. Currently unimplemented as Ebitengine does not support borderless windows. Setting this field has no effect. Track: github.com/hajimehoshi/ebiten/issues/XXXX` (research actual ebiten issue number). (4) Add deprecation notice if removal is preferred: `// Deprecated: Decorations field will be removed in v2.0.0 due to platform limitations.` (5) Add validation test: `TestWindowDecorations` in app_test.go that verifies field behavior or documents no-op status. **Validation**: `go doc WindowConfig` should show updated field type. `GOOS=windows go build -o test.exe . && ./test.exe` (on Windows) should create borderless window when Decorations=false is set (if implemented), or return clear error if unsupported.

## Conclusion

Wayne demonstrates strong engineering practices in documentation (92.1% coverage), code cleanliness (zero duplication), and architectural clarity (single-package design with clear separation between PublicWidget stable API and internal Widget interface). However, **critical functional gaps** prevent the library from fulfilling its documented promises:

1. **No verified functionality on target platforms** — Tests cannot execute on Windows, macOS, Android, or iOS.
2. **Unverifiable compatibility claim** — "100% API-compatible with wain" lacks proof.
3. **Incomplete feature implementations** — Advanced Canvas methods have visual quality limitations not disclosed to users.

**Recommended Next Steps** (Priority Order):
1. Establish CI/CD on all four target platforms to enable test execution (addresses CRITICAL #1).
2. Create wain compatibility test suite or downgrade compatibility claims (addresses CRITICAL #2).
3. Document limitations of LinearGradient, RadialGradient, BoxShadow in godoc (addresses HIGH #1).
4. Implement focus management or document as unsupported accessibility limitation (addresses HIGH #2).
5. Resolve WindowConfig.Decorations ambiguity (addresses HIGH #3).
